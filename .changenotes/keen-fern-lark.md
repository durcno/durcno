# perf(rq): narrow relation subquery projections and fix nested limit/offset

Two changes to the SQL generated by `db.query(Table).findMany/findFirst`: a
projection fix that avoids reading unused columns, and corrections to nested
`limit`/`offset` handling.

## Narrowed relation subquery projections

Each related row set is built with a `LEFT JOIN LATERAL` over a derived table.
That derived table used to select `"alias".*`, so PostgreSQL read every column of
every matched related row off the heap even when the parent projection only
referenced a few of them.

The projection is now built from the same `columns` filter that drives
`json_build_object`, so only the columns the result actually needs are read:

```sql
-- before
FROM (SELECT "posts".* FROM "public"."posts" "posts" WHERE ...) "posts"

-- after
FROM (SELECT "posts"."id", "posts"."title" FROM "public"."posts" "posts" WHERE ...) "posts"
```

The saving scales with `(parent rows x related rows)` and is largest for tables
with wide `text`/`jsonb` columns, since the unrequested ones no longer have to
be fetched and detoasted.

Alias-based `select` mode keeps the `*` projection, because the columns
referenced by a `SqlFn` expression are not introspectable. Results are
unchanged.

## Nested `limit` and `offset` corrections

Three fixes to the `limit`/`offset` options accepted inside a `with` block for
`many` relations.

`offset` was never emitted. It was accepted by the type definitions and
documented, but `buildRelationSubquery` only handled `orderBy` and `limit`, so
`offset` was silently dropped. It now renders after `LIMIT`, as PostgreSQL
requires when both are present.

`limit: 0` was dropped. The guard was a truthiness check rather than an
`undefined` check, so a zero limit never reached the generated SQL. It now
correctly produces `LIMIT 0` and returns an empty array.

`limit`/`offset` no longer inline prepared `Arg` placeholders. Nested values
were interpolated directly, which rendered an `Arg` object as
`LIMIT [object Object]` and failed with a syntax error. They now bind as proper
`$N` parameters, matching the top-level options:

```typescript
const statement = prepare(
  { lim: Arg.number(), off: Arg.number() },
  (args) =>
    db
      .prepare()
      .query(schema.Posts)
      .findMany({
        columns: { id: true },
        with: {
          comments: {
            columns: { body: true },
            orderBy: asc(schema.Comments.body),
            limit: args.lim,
            offset: args.off,
          },
        },
      }),
);
```

The shared top-level and nested limit/offset rendering is now a single
`appendLimitOffset` helper, so both paths stay in sync.
